* 问题之河

一块固定大小的内存，用来存 KV cache。有两种"加护"手段：给敏感的层多分几个 bit，或者把关键 token 留成高精度。两种手段抢同一块预算——这块预算到底怎么在它们之间切？

这个问题难，是因为过去每一代方法都只拿其中一种手段当主角，另一种要么不管，要么拍脑袋给个固定比例。"保哪些层"和"保哪些 token"看着是两个独立问题，实际是同一个预算的两种花法，花多了一边另一边就缺。

说明：本文的溯源基于目标论文自己的引言和相关工作（已读全文 PDF 的前半部分和实验部分）。前序论文的具体内容，除目标论文里写明的批判点外，是我根据对这些工作的已有了解补充的，没有逐篇重新查证；这些处会标注"不确定"。只找到约 3 层，没有凑满 5 层。

* 演化叙事

** 2024 | KIVI: 先把 KV cache 压到 2 bit 再说

*** 它看到了什么问题

长文本推理里 KV cache 比模型权重还吃显存。已有办法要么丢 token（H2O、StreamingLLM 这一路），要么整体降精度，但 key 和 value 的数值分布差别很大，一刀切地量化，精度掉得厉害。

*** 它的解法

key 里的离群值集中在少数几个通道，所以 key 按通道量化；value 没有这种结构，按 token 量化。两边各用最合适的尺子量，整体压到 2 bit。

*** 为什么这招管用（以及哪里埋了新坑）

尺子选对了，误差就小。但它对所有层、所有 token 都一视同仁——这就留下了两个方向的疑问：是不是有些 token 不该被压？是不是有些层不该被压得一样狠？这两个疑问，后来被两拨人分头回答。

** 2024-2025 | ZipCache、OTT: 少数 token 不该被一视同仁

*** 它看到了什么问题

KIVI 式的统一量化里，一小撮 token（注意力集中的"显眼"token、离群 token）一旦被压坏，输出就歪。把它们和普通 token 同等对待，不划算。

*** 它的解法

把你的预算想象成一笔钱：大部分 token 用 2 bit，但把最显眼的那几个留成高精度。ZipCache 找出显著 token，OTT 追踪并保留离群 token。

*** 为什么这招管用（以及哪里埋了新坑）

少数 token 误差贡献大，保住它们性价比高。但目标论文指出，这类方法"largely overlook the heterogeneous sensitivity of different layers"：它们假设每层都值得被同样对待。浅层和深层对精度的需求其实不一样。

** 2025-2026 | KVTuner、PM-KVQ: 层和层不一样

*** 它看到了什么问题

另一拨人从相反方向切入：不是 token 不平等，而是层不平等。有的层对量化很敏感，压到 2 bit 就崩；有的层压到 2 bit 几乎没事。

*** 它的解法

先量每层（或每个块）对量化的敏感度，敏感的给 4 bit 甚至更多，不敏感的给 2 bit，总预算不变。KVTuner 按层敏感度选配置，PM-KVQ 在块粒度上做混合精度。

*** 为什么这招管用（以及哪里埋了新坑）

和上一条线对称：这条线管住了层间差异，但目标论文批评它们"apply uniform token treatment within each layer"——层内每个 token 还是同一个精度，上一条线发现的"关键 token"红利被放掉了。

** 2026 | KVmix: 两条线第一次碰头

*** 它看到了什么问题

层的不平等和 token 的不平等同时存在，只做一边就浪费另一边的红利。

*** 它的解法

同时用上层重要性和"关键上下文"选择：层决定基础精度，另外挑出 pivotal context 做保护。

*** 为什么这招管用（以及哪里埋了新坑）

两种信号终于在一个方法里共存了。但目标论文的批评很具体：KVmix 的 token 侧"mainly focuses on context selection rather than precision allocation based on heterogeneous token importance"——它选的是"留哪些上下文"，不是"每个 token 该配几 bit、总预算怎么在层和 token 之间切"。另外，层和 token 的保护依然是两套机制各自运转，它们抢预算这件事没有被当成问题本身。

** 2026-10 | MultiAlloc: 把"怎么切预算"变成问题本身

*** 它看到了什么问题

到 KVmix 为止，所有方法都在回答"保谁"。MultiAlloc 把问题换了：层升精度和 token 保留这两种手段，吃的是同一笔预算 B。给 token 多留一点，层就得少升一点。这个切分比例本身该优化，而不是手工指定（论文的 Figure 1 和 Table 3 里，50/50、65/35、35/65 三种手工切分正是对照组）。

*** 它的解法

三步，全部离线：

1. 解耦 profiling。层侧：用一阶泰勒展开近似每层在不同 bit 下的误差对 loss 的影响（梯度与量化误差的内积）。token 侧：用 key 的 L1 范数当 token 重要性，每组 G 个 token 里保留 top-k，用"丢掉的重要性质量"估计保留 k 个的代价。
2. 预算耦合分配。枚举若干 token 保留方案 o_i；每个方案先扣掉它占的内存，剩下的预算分给层级 bit 配置（求最优 q_i*），再用 J_i = L_layer(q_i*) + L_tok(o_i) 给方案打分，取最小者。
3. 静态执行。推理时直接套用选出的 (q*, k*)，没有在线搜索。

用变形的说法：如果你把 KVmix 里"层决定基础精度 + 另挑关键上下文"这两套并行机制，改成"先固定 token 保留方案，剩余预算整体交给层，再对 token 方案做外层枚举"，你就得到了 MultiAlloc——预算成了联接两个模块的唯一耦合变量。

*** 为什么这招管用（以及哪里埋了新坑）

直觉上，这是一个两层的背包问题：外层选 token 保留量，内层给层分 bit，目标是总代价最小。它之所以比手工切分好，是因为最优切分随模型和预算而变。

论文的实验（A100，Llama-3-8B、Mistral-7B、DeepSeek-R1-Distill-Qwen-7B/14B、QwQ-32B；GPQA、GSM8K、LongBench-v2）里：Llama-3-8B 在 423 MB 预算下，与 OTT、PM-KVQ、KVmix 对比，各模型上总体平均分最高；消融里去掉任一维度都掉点；手工切分里 65/35 与 MultiAlloc 接近，论文自己解释为"恰好接近 profiling 选出的比例"。在 14B/32B 上增益较小，论文称是因为基线已逼近 FP16，MultiAlloc 缩小了 48.2% 和 52.1% 的差距。

我看到的新坑（均为我的判断，不确定是否被作者在后文处理）：
- 评估只报精度，没看到端到端延迟/吞吐。混合精度加 token 分组保留，实际 kernel 开销没有证据。
- 策略是静态的、基于校准集的，换一类任务分布是否仍然最优，没有看到论证。
- 一阶泰勒 + L1 范数都是代理指标，它们与真实精度的相关性只在最终结果里间接体现。
- 对比基线只有 3 个，且 FP16 之外没有和未压缩预算的更大范围扫描（5.4 节有多预算实验，我没读到细节）。

* 前沿延伸

截至 2026-10-14，我没有找到引用 MultiAlloc 的后续论文：它 2026-10-13 才上 arXiv。能说的是同一问题上的并行工作：KVCOBRA（Ha et al., 2026，目标论文引用）也做"固定内存下分配压缩配置"，MoE-nD（Sun et al., 2026）联合考虑量化和 token 缩减。这两篇我没有读原文，所以不判断它们和 MultiAlloc 的优劣，只能说目标论文把它们归为"优化单一策略或配置、没有建模跨粒度的共享预算"。

* 洞见

表面上是 KV cache 量化的技术迭代，底下发生的是研究对象的升级：从"怎么量化"到"保谁"，再到"保护这件事本身是稀缺资源，怎么分配"。第二步（保谁）分裂成两个山头，各自把自己那一维做深；第三步发现两个山头在抢同一块预算，于是预算成了一等公民。

这个模式在压缩领域反复出现：单一旋钮各自调到头，然后出现"旋钮之间怎么配"的问题。下一步更可能走向：把静态离线策略改成随输入自适应；把 profiling 代理指标换成更直接的度量；把 bit 之外的手段（token 驱逐、offload）也纳入同一个预算（目标论文自己把 H2O 等划为不同类问题，MoE-nD 已在往这个方向走）。

* 启发

读一个领域时，可以问"现在的方法在各自优化什么，它们共用什么稀缺资源"。如果几条并行路线其实花的是同一笔预算，那么"预算怎么切"本身就可能是一篇论文。这意味着你可以在自己的方向上列出各个"旋钮"，看它们是否共享同一个约束，再判断有没有人把这个约束显式建模。

对 llm-paper-radar 的实际用途：评估后续同类论文时，先看它的基线是否包括 KVmix 这类混合粒度方法，以及是否报了端到端延迟——这两点是 MultiAlloc 当前最薄弱的地方。
