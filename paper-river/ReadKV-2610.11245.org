* 问题之河

KV cache 有个很别扭的结构：你把一个 token 的 key/value 写进缓存的时候，根本不知道以后哪个 query 会来读它、需要多精细的精度。写的时候是"盲写"，读的时候才知道"这次到底要不要这么细"。

现有做法基本都在"写的时候"就把这件事定死了：要么统一压成固定的 2 bit/4 bit，要么用历史注意力猜哪些 token 重要、写的时候就给它多分点精度。可是"写的时候重要"和"这次 query 需要精细"根本是两回事——同一个 token，这次 query 可能完全用不上它的细节，下次 query 又可能非它不可。一旦在写入阶段就把精度焊死，无论焊得多聪明，都会有要么浪费、要么不够用的情况。

这条问题线真正的核心是：*能不能让"存多细"和"每次读多少"彻底脱钩*——存的时候留足余地，读的时候让每次的 query 自己决定要看多细？

* 演化叙事

** 2024 | KIVI: 给 key 和 value 分别找到"该怎么分组量化"

*** 它看到了什么问题

在 KIVI 之前，大家压缩 KV cache 基本是"一视同仁"：不管是 key 还是 value，用同一套量化方式怼下去。但 KIVI 的作者去看了真实 LLM 里 key 和 value 的元素分布，发现这两者的"形状"完全不一样——key 在某些固定的 channel（维度）上会反复出现离群值，而 value 的离群模式是按 token 走的，不是按 channel 走的。用同一套量化策略去套两种完全不同的统计结构，就像用一把尺子量两种不同形状的东西，总有一边量不准。

*** 它的解法

KIVI 不再"一刀切"：key 按 channel 分组（同一个 channel 里所有 token 的那个维度放在一起量化），value 按 token 分组（同一个 token 里所有维度放一起量化）。再加一个保留最近 128 个 token 全精度的 residual buffer 兜底。整个方案做成了统一的 2-bit 定长编码，写进去之后所有以后的 query 读的都是这同一份 2-bit 数据。

*** 为什么这招管用（以及哪里埋了新坑）

管用是因为它第一次承认了"key 和 value 不是一回事"，分组方式对齐了数据本身的结构，所以同样是 2-bit，却比"一视同仁"的量化误差小得多。

但坑也很明显：精度是*写入时*就焊死的定长码（fixed-rate code）——不管后面哪个 query 来读，都原样读回这同样的 2 bit。如果某个 query 根本不需要这么细，这些 bit 还是要被搬一遍；如果某个 query 恰好需要更细，这 2 bit 又不够用。"每次都读一样多"这件事，KIVI 完全没有触碰。

** 2024 | SparQ / Quest / Loki：与 KIVI 并行的另一条思路——不是压得更细，而是选得更准

*** 它看到了什么问题

这几篇论文（并非直接批评 KIVI，而是从另一个角度切入同一个大问题）注意到：就算你把每个 token 的精度都分配得无比精巧，一次 decode 其实根本用不上所有历史 token——attention 本来就集中在一小撮 token 上。那为什么要把所有 token 的数据都搬一遍？

*** 它的解法

SparQ 先用 query 相关的 key 特征粗略估计一下 attention 分布，挑出看起来重要的那部分 token，再去精确取它们的 value。Quest 把 cache 按 page 分块，用压缩过的 page 摘要给每个 page 打分排序，只取 top 的几个 page。Loki 用低维的 key 信息做类似的筛选。三者共同点：*这次该读哪些 token，由当前 query 决定*，而不是写入时就定好。

*** 为什么这招管用（以及哪里埋了新坑）

管用是因为它换了一个维度做选择——不是"每个数读多细"，是"这次到底要不要读这个 token"。两者正交，理论上可以叠加。

新坑：这是个"全有或全无"的选择——一个 token 要么整个被读（包括它的全部精度），要么干脆不读。没有"读一半""读个大概"这种中间状态。而且它只决定"读哪些 token"，完全没有回答"存的时候到底该留几档精度备用"这个问题。

** 2025.03 | Xie et al.：在硬件内存控制器里，把"分档存"和"按需取"拼到一起

*** 它看到了什么问题

Xie 等人站在系统/硬件的视角看这件事，发现了一个被忽略的拼图：量化、剪枝、token 选择这些"有损"方法都在拿推理质量换内存，但软件层的无损压缩（LZ4、ZSTD）用在浮点权重和 KV cache 上几乎不起作用——因为一个浮点数的指数位和尾数位是交织在一起存的，字节层面看起来就是高熵噪声，压缩算法找不到可压的规律。更麻烦的是，就算你做了动态量化（不同 token/层用不同精度），也没有机制保证内存带宽真的按比例降下来——精度降了，但硬件该搬的数据量没有同步降。

*** 它的解法

他们把 KV cache 按精度拆成多个"位平面"（bit-plane）存储——相当于把一个数的高位、次高位……拆开分层放。KV page 排出重要性等级，内存控制器根据当前 query 的需求，*只搬运需要的那几个位平面*，而不是整条数据原样搬一遍。这件事是在内存控制器硬件层面透明完成的，几乎不需要改计算框架和软件栈。

*** 为什么这招管用（以及哪里埋了新坑）

管用是因为它第一次把"存的时候留多档精度"和"读的时候按需只取一部分"这两件事真正拼在了一起——不再是 KIVI 那种"写时焊死"，也不再是 SparQ/Quest 那种"全有或全无"的 token 级选择，而是精度这个维度本身变得可以"按需取用"。ReadKV 论文直接承认这是它"最接近的系统先例"。

新坑：这套机制是以 page 为粒度、靠硬件内存控制器实现的"按精度等级取舍"，没有理论上的最优性保证——没人证明这种取舍方式在数学上是不是已经是最好的；而且它的粒度是 page（一批 token 一起决定），没有做到每个 key channel、每个 value token 都能有自己独立的读取深度。

** 2026.10 | ReadKV（目标论文）：把"按需取精度"做成可证明最优的、标量粒度的渐进码

*** 它看到了什么问题

ReadKV 直接站在 Xie et al. 的肩膀上往前走：你已经证明了"存的精度"和"读的精度"可以分开，但——

1. 你的选择粒度是一整个 page，没有做到每个 key 的每个 channel、每个 value 的每个 token 都独立决定读多深；
2. 你的分配规则没有理论保证，不知道这种硬件层的位平面取舍方式，相比"理论上最优的按需读取"差多少；
3. 你只用 query 信息去选 page，没有用上"算出 attention 之后，还能再用 attention 结果去决定 value 该读多细"这第二层反馈。

*** 它的解法

ReadKV 把每个 key、value 的标量值编码成一棵二叉量化树上的一条路径（渐进码）：路径的前两位已经能给出一个粗略重建，读到第三位就更精细一点，一路读到第 W 位（比如 8 位）就是最精细的版本。同一份存好的编码，不同的 query 可以读不同长度的前缀，读得越长越精细，但存的那份数据从头到尾不用改写。

读取分两阶段：第一阶段，当前 query 直接决定每个 key channel 该读多深（query 在哪个维度上系数大，就说明这个维度对这次的 attention score 影响大，就该读深一点）；第二阶段，用第一阶段重建出来的 key 算出一次 attention 权重，再用这个权重决定每个 value token 该读多深（attention 权重大的 token，它的 value 该读深一点）。整个分配规则是"每次把下一个 bit 预算，分给预期误差下降最多的那个 channel 或 token"，论文证明了在"精度收益递减"的条件下，这种贪心分配恰好是全局最优解。

*** 为什么这招管用（以及哪里埋了新坑）

管用是因为它把 Xie et al. 那种"硬件层、page 粒度、靠工程直觉"的位平面选择，升级成了"算法层、标量粒度、有理论最优性证明"的渐进编码分配。而且它还多走了一步：用重建出来的 attention 结果去指导 value 的读取深度——这是前面所有方法都没有的"query→key精度→attention→value精度"这个两阶段反馈链条。实验上，8-bit 存、平均读 4-bit，C4 困惑度只比不压缩差 0.66%，比同等读预算下"老老实实存读 4-bit"的方案更准；在 A10G 单层场景下比 TurboQuant 这个同期的定长量化编码延迟低 39%。

新坑（论文自己也承认）：理论上的"分离优势"目前只在特定的有限维模型族里证明过，没有扩展到任意 attention 分布；A10G 上的延迟优势是单层测试结果，还没有做到端到端整个推理服务的延迟验证；而且要真正发挥长上下文、大 batch 场景下的收益，还需要把"选择、重建、attention 计算"这几步融合起来，这是论文明确留给未来工作的方向。

* 前沿延伸

论文 2026-10-08 才发布（比写这篇笔记早一天），搜索未发现任何引用或后续论文——确实太新了，还来不及有后续工作跟进。

同期（2026 年）还有一批"写时自适应精度"的论文仍在推进另一条分支——PM-KVQ（用整数规划在 Transformer block 间分配存储精度）、MixKVQ（query 重要性 + 量化敏感度决定 key channel 精度，带懒更新机制）、RDKV（prefill 后算注意力敏感权重，用反向灌水法分配存储 bit，甚至允许 0-bit 直接驱逐）。这些论文和 ReadKV 站在同一个问题场域里，但走的是"写的时候更聪明地分配"这条路，没有触碰"读的时候按 query 临时决定精度"这个 ReadKV 和 Xie et al. 共同开辟的维度。换句话说，这条"读时自适应"的分支目前只有 Xie et al. 2025 和 ReadKV 两个节点，是条还很新、很窄的路，截至目前 ReadKV 是这条线上最新的进展。

* 洞见

这条线真正在发生的变化，不是"量化越做越细"这种表面迭代，而是一个认知框架上的转变：*大家逐渐意识到"存"和"读"本来就是两个独立的预算，没必要绑在一起*。KIVI 还活在"存多少就得读多少"的世界里，精度是写入时一次性决定的命运。SparQ 们把"要不要读"这件事解放了出来，但还没碰"读多细"。Xie et al. 把"读多细"也解放了出来，但解放的方式是硬件层面、粗粒度的。ReadKV 把这件事做到了最细的粒度（每个标量）、最严谨的程度（可证明最优）。

这其实是一个很常见的研究演化模式：*一个被想当然捆在一起的决策（存=读），先被某个领域（硬件系统）用工程手段局部拆开，再被另一个领域（理论+算法）用数学工具彻底拆开、做到极致*。Xie et al. 证明了"拆开是可行的"，ReadKV 证明了"拆开之后能做到多好"。

下一步最可能的方向，论文自己也点明了：把"选择、重建、attention 计算"这三步融合成一个硬件/软件协同的流水线（而不是分开的三步），这样才能把理论上的读预算优势，变成端到端真正的推理延迟优势——这也是为什么 Xie et al. 那种硬件内存控制器的视角，未来很可能会和 ReadKV 这种算法层的视角重新合流。

* 启发

当你发现一个领域里"两个决策总是被绑在一起处理"（这里是"存的精度"和"读的精度"），不妨问一句：*它们是不是本来就可以分开，只是没人试过把它们正式拆开建模*。KIVI、SparQ 这些论文都是在"存读绑定"这个默认框架里做优化，而真正的范式跃迁来自 Xie et al. 和 ReadKV 这种"先把框架本身拆开，再在拆开后的空间里重新优化"的动作。

这意味着你在读一篇论文时，除了问"它把某个指标优化到多好"，更值得问"它默认绑定在一起的两个变量，是不是其实可以解耦"——解耦本身往往就是下一次突破的起点，而把解耦做到可证明最优，是把一个工程直觉（Xie et al. 的位平面选择）升级成一个理论贡献（ReadKV 的渐进码分配）的标准路径。
