* 问题之河

长上下文推理时，模型每生成一个字都要把之前所有的 key-value 缓存扫一遍——这事越来越贵，贵到成了瓶颈。于是大家把缓存切成一页一页的"页"，每页只存一个压缩摘要，推理时先看摘要猜哪几页有用，只读这几页，省掉大头的数据搬运。

问题是：这个摘要该存什么？如果摘要存错了东西，猜页就会猜错，模型输出就会跑偏。一代一代人前赴后继，答案越收越窄，最后收敛到一个很反直觉的点上：大家以为"摘要要尽量保真地还原 key 本身"，但其实最终影响输出的不是 key 本身，而是 key 和 value 搭配之后算出来的那个 attention 结果。这条河就是从"该用什么规则删 token"一路走到"该用什么基来描述一页"的演化。

* 演化叙事

** 2019 | Sparse Transformer: 训练时就把注意力模式定死

*** 它看到了什么问题

Transformer 的注意力是全连接的——每个位置都要跟之前所有位置算一遍相关度，序列一长，算力和缓存开销就是平方级增长。Reformer、FlashAttention 这类方法想办法省计算，但缓存本身还是要存满；Sparse Transformer 换了个思路：干脆让每个 token 只看固定的一小撮位置（比如本地窗口 + 跨步采样），从结构上砍掉大部分连接。

*** 它的解法

把"全看"变成"按规则看"——位置 i 只和一组预先定好的位置集合算注意力，这组规则在训练时就定死，和具体内容无关。

*** 为什么这招管用（以及哪里埋了新坑）

规则定死了，计算量自然降下来了，这对"从头训一个稀疏模型"是有效的。但后来者发现：如果直接把这套定死的模式套到一个已经训练好的大模型上做推理（而不是重新训练），miss rate 很高——定死的模式不知道这次生成到底需要看哪里，内容对了它可能没看，内容不对它偏偏看了。这个"规则和内容脱节"的坑，留给了下一代。

** 2023 | H2O: 别死守规则，动态看哪些 token 真正重要

*** 它看到了什么问题

固定稀疏模式对当前生成的内容视而不见。H2O 的作者换个角度想：既然模型在生成过程中会不断对某些 token 给出很高的注意力分（"Heavy Hitters"，重击手），那干脆就动态跟踪这些分数，谁攒的分高就留谁，谁没攒到分就从缓存里删掉——不再是训练前定好规则，而是跑的时候现场判断。

*** 它的解法

把 KV 缓存淘汰问题建模成一个"动态子模优化"问题：每一步决策"删哪些 token、留哪些 token"，用累积的注意力分数做依据，理论上能证明这套贪心策略有保证。

*** 为什么这招管用（以及哪里埋了新坑）

因为它看内容而不是看位置，所以比固定模式更准——至少当下重要的 token 大概率能留住。但这里有个致命的副作用：删掉的 token 是真的从缓存里消失了。如果某个 token 现在看起来不重要，但后面生成到某一步突然又需要用到它（比如长文档里前面提过一次的关键信息，后面才被引用），那它已经被永久删除，想找都找不回来了。这就是"永久丢失信息"的坑，留给了下一代去填。

** 2024 | Loki: 不删 token，换个空间里便宜地打分

*** 它看到了什么问题

H2O 的淘汰策略治标不治本——只要是"删"，就有"删错了再也救不回来"的风险。Loki 的作者观察到一个现象：key 向量虽然维度很高，但实际上"活"在一个低维子空间里，不同数据集、不同模型上这个现象都一致存在。

*** 它的解法

拿一批校准数据对 key 做 PCA，只用排名靠前的那几个主成分方向做近似打分——先在这个低维空间里快速算出"哪些 token 大概率重要"，选出候选 top-k 之后，再对这一小撮候选 token 用完整维度精确计算。整个过程 token 本身一个都不删，只是打分的时候借了个低维的"近道"。

*** 为什么这招管用（以及哪里埋了新坑）

低维打分省了大量内存搬运和计算，而且因为不删 token，信息永久丢失的问题消失了。但 Loki 用的这个 PCA 基是全局共享的——用同一份校准集算出来的同一套主成分方向，套用到缓存里所有的页、所有的位置上。后来者用数学证明指出：任何一个固定共享的低维投影，都必然存在"内容盲区"（page-content blind directions）——不管输入内容具体是什么，总有一些方向这个共享基压根看不见，不管给它多大容量都补不回来。这就是"基该是共享的还是局部的"这个新坑，留给了下一代。

** 2026-07 | LOCKS: 每一页自己的基，而不是大家共用一个

*** 它看到了什么问题

LOCKS 的作者系统性地证明了：Loki 这种全局共享基、ShadowKV 这种按整个序列算一个基的方法，本质上是同一类问题——"代表性的范围选错了"。哪怕把共享基做得再大，也补不回局部基能看到的保真度，因为结构根本不在那个尺度上存在。同时他们还指出 Quest 这类"极值统计"（min/max）方法的问题：平均意义上看起来还行，但恰恰在那几页真正藏着答案的页面上会漏掉；COBS/SPLA 这类二阶矩统计方法则只能刻画"类高斯"的平均特征，在信息最集中、最"尖"的那几页上控制力最弱。

*** 它的解法

把"共享一个基"换成"每一页自己算一个局部谱基"——每页的 key 单独做 SVD/PCA，只保留这一页自己最重要的方向，摘要大小约是整页缓存的十分之一。选页时不用读候选的 key 或 value，而是用这份局部谱基重建页内的 logit，再用 log-sum-exp 估算整页的注意力质量，排序选 top 页。

*** 为什么这招管用（以及哪里埋了新坑）

局部基彻底解决了"内容盲区"——每页的摘要就是为这一页量身定制的，不存在共享基那种结构性盲区，长文档 QA、检索密集型任务、长程推理任务上都比共享基/极值统计/矩统计的方法稳。但 LOCKS 选基的标准还是只看 key 的能量/方差——"这个方向上 key 的信息量大不大"。后来者指出：这个标准测的是"logit 还原得准不准"，而真正决定模型输出对不对的，是 key 和 value 搭配之后算出来的、按注意力权重加权的 value 输出。一个方向上 key 的方差很大，不代表这个方向对最终输出重要；一个方差很小的方向，反而可能是输出的关键。这个"该测 key 还是该测 key-value 联合"的错位，就是下一代要填的坑。

** 2026-10 | OVAL: 选基的时候，把 value 也算进去

*** 它看到了什么问题

OVAL 的作者把 LOCKS 这条"每页一个局部谱基"的结构留了下来，但点出了它的核心盲点：这类方法在设计打分标准时，瞄准的是"估计注意力分数/页相关度有多准"，但这些目标并不直接衡量"近似误差对最终的、按 value 加权的注意力输出影响有多大"。换句话说，选基这件事一直在给一个错的目标做优化——保真的是 logit，不是输出。

*** 它的解法

构造一个"输出感知"的页编码：从 key 和 value 的联合几何结构里，推导出页内 logit 扰动对条件注意力输出的精确敏感度，再据此挑选真正影响输出的方向来构建每页的基——而不是只挑 key 自身方差大的方向。关键的工程约束是：这套方法在推理时不存储任何 value 相关的统计量，解码时的打分开销和"纯 key 谱表示"（也就是 LOCKS 的方案）完全一样大、一样快，只在真正要重建页摘要的那一刻才用到 value。他们还把误差拆成两种：一种是"条件注意力输出误差"（局部一阶），一种是"页对数质量/检索误差"（局部二阶），用一个混合目标把两种误差都兼顾到。

*** 为什么这招管用（以及哪里埋了新坑）

因为选基标准直接对齐了"输出误差"而不是"logit 误差"的代理目标，在长程推理这类对微小误差敏感的任务上比纯 key 谱基线稳定地更好，同时没有增加解码时的开销——这是它最想证明的"白嫖"性质：多看了 value，却没多花钱。截至目前（论文发布仅一天），还没有检索到任何批评或改进它的后续工作；它的局限大概率也会落在类似的地方——比如这套"输出敏感度"的一阶近似在超长依赖、多跳推理的场景下是否仍然成立，是留给未来检验的问题。

* 洞见

这条线真正在变的，不是"算法变聪明了"，而是*优化目标离真正关心的东西越来越近*。从"按位置删"到"按注意力分删"是第一次逼近——开始看内容了；从"删"到"不删只打分"是第二次逼近——开始尊重信息不可逆这件事；从"全局基"到"局部基"是第三次逼近——开始尊重内容的局部性；从"测 key"到"测 key-value 联合输出"是第四次逼近——终于把代理目标和真实目标对齐了。每一代人都以为自己找到了终点，下一代人总能指出："你优化的那个东西，其实不是你真正想要的东西。"

下一步最可能往哪走：现在"输出感知"还是局部一阶近似，而且只在构建页摘要那一刻才看 value、推理时不存 value 统计——这意味着它对"value 分布在生成过程中剧烈变化"的场景（比如长链推理里前后内容强相关、误差会累积放大的任务）未必还成立。下一代大概率会去挑战这个一阶近似在多步误差累积下是否依然可靠，或者去问：能不能在不增加存储的前提下，让这个敏感度估计本身也跟着生成过程自适应更新。

* 启发

这条演化线的套路，几乎每一步都是同一个动作："去问，我现在这套评分标准，到底是不是我真正关心的那个量的忠实代理？" 每次发现"评分标准"和"真正目标"之间有缝隙，就是下一个工作的起点。

这意味着你在看任何一个"用代理指标做决策"的系统（不只是 KV 缓存——推荐系统的点击率代理转化率、RLHF 的奖励模型代理人类偏好）时，都可以问同一个问题：这个代理指标，在哪些具体场景下会和真实目标分道扬镳？找到那个分道扬镳的具体场景，往往就是下一篇论文的起点。
