* 问题之河

一个 agent 开着一个几十万甚至上百万 token 的会话挂在那儿聊了几个小时，服务器上还同时挂着好多个这样的会话。它的历史记忆（KV cache）大到 GPU 显存装不下了，只能搬到主机内存里。这时候，模型每吐一个新词，都得先去主机内存里"扫一遍"所有历史 token，看看这次到底该看哪几个——这一"扫"的流量，就成了拖慢生成速度的瓶颈。

这个问题从 2023 年开始就有人在啃：怎么让模型不用每次都把整个历史记忆读一遍就能知道该看哪儿？大家想出的招数一代比一代聪明，但都卡在同一个地方——不管用什么办法去猜"这次该看哪些历史"，这个"猜"的动作本身，也得先摸一遍全部历史的某种压缩版本，而这个"摸一遍"要花多少流量，是提前钉死的、对每次提问都一样多。这篇目标论文要问的就是：这个"扫描预算"，能不能不是一刀切，而是每次提问自己决定该花多少？

* 演化叙事

** 2023 | H2O / StreamingLLM: 扔掉不重要的记忆

*** 它看到了什么问题

Transformer 解码本来就是"带宽受限"的活——每吐一个词，都要把整个模型权重读一遍，长上下文时还要把整个 KV cache 读一遍。当 KV cache 跟着对话变长，它的读取成本线性增长，很快就成了压死骆驼的最后一根稻草。

*** 它的解法

H2O 的作者发现一个规律：绝大多数注意力分数其实只集中在一小撮 token 上（呈幂律分布），95% 以上的 token 其实没那么要紧。既然如此，干脆动态地把"不重要"的 token 从 KV cache 里删掉，只留"重量级选手"（heavy hitters）加上最近的几个。StreamingLLM 走的是更省事的路子：连"谁重要"都不用算了，固定留最前面几个 + 最近一个窗口就行。

*** 为什么这招管用（以及哪里埋了新坑）

这招管用是因为注意力确实稀疏——省下的显存和带宽是实打实的（论文里报的吞吐量提升到了 29 倍）。但它埋了一个很深的坑：驱逐是*不可逆*的。这次提问觉得某段历史不重要，把它删了；但如果十步之后另一个问题恰好需要那段历史呢？答案已经不在了。后来 Quest 等工作也点出这个毛病：H2O、StreamingLLM 这类方法会在看到"问题"之前就已经把"答案"所在的那段历史给扔了。

** 2024 | SparQ / Loki / Double Sparsity: 一条都不删，但只扫"缩水版"

*** 它看到了什么问题

既然删了就回不来，那就别删。但如果每次都把完整的 KV cache 全部读一遍再决定看哪些，那压缩就没意义了——FlexGen 式的"全量算精确分数再选 top-k"最多只能省一半的读取量，因为选之前那一遍全量扫描跑不掉。

*** 它的解法

三篇论文（同期、独立提出）用的是同一个思路："先扫一个便宜的、缩水版的 key 表示来给所有历史 token 打分，选出这次的 top-k，再去读这 top-k 的完整精度"。差别只在于这个"缩水版"怎么造：

- SparQ 让每个 query 自己挑出它认为最重要的 r 个通道（按 |q| 最大排序）；
- Loki 提前用校准数据把 key 转到 PCA 基里，只看前 r 个主成分；
- Double Sparsity 离线选好一批"标签通道"，所有 query 统一使用。

*** 为什么这招管用（以及哪里埋了新坑）

管用是因为"打分"用的信息量远小于"完整读取"的信息量——扫一遍缩水版的成本，比读全量 key 便宜得多，同时因为一条历史都没删，理论上不会有 H2O 那种"答案被提前扔掉"的硬伤。

但新坑在这里：不管选中的是哪 r 个通道，读取深度是*统一钉死*的——三篇论文都是"选中的通道，全部读到同一个比特数"（在 4-bit 量化下都是 136 bit/token 左右）。可是同一个 query 对不同通道的在意程度并不一样：有的通道对这次打分至关重要，值得多花几个 bit 去读准；有的通道虽然被选中了，但边际价值已经很低，读那么多 bit 纯属浪费。这个"一刀切的读取深度"，就是 Fathom 要下手的地方。

** 2026 | Fathom: 让每个通道自己决定读多深

*** 它看到了什么问题

SparQ/Loki/Double Sparsity 都在纠结"选哪几个通道"，但选完之后所有通道的读取深度是一样的。而事实上，量化误差是随比特数指数下降的（每多读一个 bit，误差降到原来的 1/4）。一个重要通道的第一个 bit，比它自己的第四个 bit 值钱得多；而一个次要通道的第一个 bit，可能比重要通道的第四个 bit 还值钱。换句话说，"选通道"这个二元决定（读 or 不读）本身就太粗糙了，真正该省的是"该读的通道里，具体读几个 bit"。

*** 它的解法

Fathom 把 4-bit 的 K cache 按"位平面"（bit-plane）方式重新组织存储：每个通道的前 t 个位平面，天然就等价于该通道的一个精确的 t-bit 量化器，不需要另外存一份低精度副本。有了这个存储结构，每个 query 就可以把自己的"读取预算"按"逆向注水"（reverse water-filling）的规则，按各通道对这次打分方差的贡献大小，分配到不同的读取深度上——重要通道多读几个位平面，次要通道少读甚至不读。这本质上是把"固定深度、二元选择"变成了"连续深度、按重要性动态分配"的一个连续化升级。

*** 为什么这招管用（以及哪里埋了新坑）

管用是因为它把 SparQ 等方法里被浪费掉的那部分"读取预算"重新分配到了真正值钱的地方——同样的字节数，读得更准；同样的准确度，读得更少。论文里报的数字是：在 100 万 token 的上下文下解码单步快 1.67 倍，在同样的 GPU 时间下比 SparQ 的 68-bit 读取方案少读 18% 的字节，误差还更低。

它自己也诚实地指出了新的边界：这个优化只在"KV cache 和排序索引都在主机内存里"这个场景下才有意义——如果索引本来就在 GPU 显存里，扫描已经不是瓶颈了，这套"省字节"的把戏就不再带来时间上的好处。这也许就是下一个问题的起点：怎么把"按重要性动态分配读取深度"这个思路，用到索引本身就在 GPU 上、瓶颈变成算力而不是带宽的场景里。

* 前沿延伸

Fathom 发布于 2026-09-17，距今检索时仅一天时间，尚未检索到引用它并提出改进的后续论文。截至目前，这是这条"扫描预算怎么按需分配"演化线上的最新进展。

另外两条与之平行、但主线之外的分支值得一提（论文自己也把它们标注为"另一个杠杆"，不在这条问题的主线上）：
- "少扫一些东西"这条杠杆：Quest（按页打分）、ShadowKV（按块打分+低秩K）、InfLLM（按块代表token打分）——它们省的是"扫描单位的数量"，而不是"每个单位读多深"，与 Fathom 正交。
- KV cache 量化这条杠杆：KIVI、KVQuant、TurboQuant 在压缩"存下来的这份 cache 本身"；Any-Precision LLM 提出的"位平面存储让前缀等于低精度模型"这个想法，被 Fathom 直接借用到了 K cache 的存储结构设计上。

* 洞见

这条线其实是同一个优化问题在三个不同"粒度"上被反复求解：先是 token 粒度（留哪些 token），再是通道粒度（看哪些维度），现在是比特粒度（每个维度看多细）。每一次演化，都是把上一轮"一刀切"的那个二元决定，换成了一个连续的、按重要性加权的分配问题——H2O 的"留/删"被 SparQ 们软化成"选哪 r 个"，现在 Fathom 又把"选中的通道读多深"从"固定深度"软化成了"逆向注水"的连续分配。

这背后真正的模式是：只要还有一个"提前钉死的预算"（不管是要删的 token 数、要选的通道数、还是要读的 bit 数），后来者大概率会想办法把它变成"按重要性动态分配"的问题——因为静态预算总会在某些 query 上浪费、在另一些 query 上不够。下一步最可能走的方向，就是论文自己点出的那个边界之外：当瓶颈从"带宽"换成"算力"（索引本身就在 GPU 显存里）时，这套"按重要性分配预算"的思路要怎么改造，才能在算力受限而不是带宽受限的场景里也管用。

* 启发

这条演化线给"怎么找问题"的启发是：当你看到一个领域里所有方法都在用同一个"提前钉死的参数"（不管是阈值、数量还是精度），先别急着去优化这个参数本身怎么调，而是问一句——这个参数有没有可能因为使用场景（这里是"每次提问"）不同而不同？如果答案是"有可能"，那就意味着你可以把一个静态的超参数问题，重新表述成一个动态分配问题（比如这里的"逆向注水"），这往往是一个新论文的起点，而不需要发明全新的机制。
