* 问题之河

Agent 跑起来之后，KV cache 的脾气跟聊天机器人完全不一样。聊天场景里一问一答，上下文不长；但一个"持续浏览网页/反复调用工具/改代码"的 agent，会把同一段几万 token 的系统提示和历史对话，在几十个来回里反复复用——KV cache 既要长时间占着显存不被挤掉（cache residency），又要同时伺候几十个并发请求把 GPU 喂饱（concurrency）。这两件事一起逼着一个问题：能不能把 KV cache 的每个数值从 16 bit 压到 4 bit，同时不把任务做对的能力搭进去，还要让这套压缩格式跑起来比不压缩更快，而不是用软件开销把省下来的内存带宽又吃回去。

这篇目标论文说得很直白：单独看"压缩率"或者单独看"精度"都不够，必须把"任务质量、cache 能不能留得住、吞吐量"这三件事绑在一起测，因为前人的工作往往只做到了其中一两样——要么有一个精度极好但跑得慢的压缩算法（当"质量锚点"），要么有一个跑得飞快但压缩率有限的部署方案（当"部署锚点"），两边各自往前走了很远，却从来没人把它们对接起来，专门为 agent 这种长上下文、高并发的场景做一次联合优化。

* 演化叙事

** 2024 | KIVI / KVQuant：K 和 V 根本不是一回事，别用同一套量化方案伺候它们

*** 它看到了什么问题
把 K 和 V 都用同一套"算个 min/max、按固定 bit 数均匀切格子"的量化方案去压，在 8-bit、4-bit 时还凑合，往 2-3 bit 走就开始崩。KIVI 的团队做了个很朴素的实验：分别看 K 和 V 在各个维度上的数值分布，发现 K 有少数几个通道(channel)数值始终异常地大，这些通道如果和其他通道混在一起按 token 分组量化，会把整组的量化范围撑大，连累所有正常通道的精度；而 V 没有这种固定异常通道，但 V 是直接乘到注意力权重上加权求和的，误差会被不同 token 的权重直接放大。换句话说：K 的误差来源是"少数通道方向"，V 的误差来源是"直接参与输出混合"——这是两种完全不同的敏感性。

*** 它的解法
KIVI 让 K 按"通道"分组量化(per-channel)——把异常通道的误差关在它自己通道里，不去连累别的通道；V 按"token"分组量化(per-token)——保证每个参与加权求和的 V 向量内部量化误差均衡。KVQuant 在同一条思路上加码：在 RoPE 旋转位置编码*之前*就量化 Key（避免 RoPE 把本来规整的分布搅乱），用非均匀、按每层敏感度加权的码表代替均匀网格，再对每个向量单独把少数几个真正的异常值拎出来单独存成稀疏项——一路把精度顶到 3-bit 时困惑度(perplexity)退化小于 0.1。

*** 为什么这招管用（以及哪里埋了新坑）
"K 和 V 不对称处理"从此成了 KV cache 量化领域的共识起点——几乎所有后来的方法都在用这个前提。但这两篇论文的具体实现仍然建立在"均匀或校准非均匀网格 + 显式存储量化常数(min/max 或 zero-point/scale)"之上。block 越小、精度要求越高，这些量化常数本身占的 bit 数开销就越显著——在 1-2 bit 这种极端区间，常数开销甚至可能比数据本身占的 bit 还多。这个"开销"问题，被下一篇论文直接当成了主攻目标。

** 2024 | QJL：别存量化常数了，用随机投影直接给你一个无偏估计量

*** 它看到了什么问题
传统的按块量化（不管是均匀还是非均匀网格）都要为每个 block 存一个 scale、有时候还要存一个 zero-point，这些"元数据"在正常 bit 数下是可以忽略的小开销，但当你想把 K/V 压到 1-2 bit 时，这点"可以忽略"的开销就变得和数据本身一样重。

*** 它的解法
QJL 把 Johnson-Lindenstrauss 随机投影（一种经典的保距降维变换）当作预处理，把向量投影之后直接取符号位，压成 1 bit——由于 JL 变换本身的数学性质，只需要对其中一个向量做这个变换、另一个向量做普通的（不量化的）JL 投影，就能拿到内积的无偏估计量，而且全程不需要为每个 block 额外存任何缩放常数或零点，实现了"零开销"的量化。

*** 为什么这招管用（以及哪里埋了新坑）
在极端的 1-bit 区间，QJL 比传统按块量化省了那部分"看不见的常数开销"，在多个模型和任务上把 KV cache 压缩超过 5 倍还不掉点。但 QJL 本质上是为"要内积、要省到 1 bit"这个特定场景设计的，它直接把向量压到符号位，牺牲了在 3-4 bit 这种"性价比甜区"里继续精修精度的空间——这块甜区，恰恰是接下来 TurboQuant 要去抢占的阵地。

** 2025/2026 | TurboQuant：旋转先把异常值打散，再用信息论最优的码表去编码，QJL 留着去偏

*** 它看到了什么问题
在 2-4 bit 这个区间，想要把失真率逼近信息论给出的理论下界，光靠一个 MSE 最优的标量量化器是不够的——因为 MSE 最优量化器本身在做内积估计的时候会引入系统性偏差，而注意力机制算的恰恰是 Q 和 K 的内积。换句话说，"量化误差小"不等于"内积估计准"，这中间差了一步。

*** 它的解法
TurboQuant 是个两阶段流水线：第一步，对向量做一次随机旋转（Hadamard 式的结构化旋转），旋转之后每个坐标会集中到一个近似独立的 Beta 分布（在典型 head 维度下很接近高斯分布），这样就可以对每个坐标独立套用 Lloyd-Max 最优标量量化器，而不用管坐标之间的相关性；第二步，把第一步量化之后剩下的残差，再过一次 QJL 变换做去偏修正，拼出一个无偏的内积估计量。数学上可以证明，这套组合拳得到的失真率只比信息论最优下界差一个约 2.7 倍的常数因子——KV cache 场景下，3.5 bit/通道几乎无损，2.5 bit/通道只有轻微掉点。

*** 为什么这招管用（以及哪里埋了新坑）
这是目前为止（旋转+码表这条线上）精度最好的方案，也是目标论文选它当"质量锚点"的原因。但它的码表是通过 Lloyd-Max 算法校准出来的一组离散质心，要把一个连续向量编码/解码成码表索引，天然需要查表(lookup)操作——这在 GPU 上意味着不规则的内存访问模式，没法直接喂给矩阵乘法单元。离线跑一遍算困惑度，这套开销无所谓；但真要在 serving 系统里一边解码一边喂给矩阵核，查表开销就会啃掉内存省下来的带宽收益。TurboQuant 证明了"精度能做到多好"，但没有回答"这么好的精度能不能跑得快"。

** 2023-2026 | 部署这条线：PagedAttention → vLLM FP8 KV cache → OCP Microscaling/CDNA4 → 自家的 TurboQuant 落地博客

*** 它看到了什么问题
和"质量锚点"这条线平行发展的，是一条"部署锚点"的线，关心的问题完全不同：KV cache 的压缩收益能不能真正落地成吞吐量，而不只是离线精度报告里的一个数字。2023 年的 PagedAttention 首先把"KV cache 该怎么在显存里摆放、能不能像操作系统分页一样按需分配"变成了一个系统问题，而不只是"每个数值占几个 bit"的压缩问题。随后 vLLM 把 FP8 KV cache 做成生产级功能：FP8（E4M3）本身就是 GPU 矩阵核原生支持的格式，量化/反量化几乎零额外开销，换来"近乎无损、大约 2 倍压缩"的确定性收益——这就是目标论文选它当"部署锚点"的原因：简单、快、但压缩率有限，4-bit 那部分增益完全没碰到。

同时，OCP（开放计算项目）2023 年发布的 Microscaling(MX) 格式规范，把"4-bit 浮点数据 + 每 32 个元素共享一个 8-bit 幂次缩放因子(UE8M0)"定义成跨厂商标准——UE8M0 没有尾数位，反量化就是一次位移操作，几乎免费，这正好是 AMD CDNA4 架构里 scaled-MFMA 指令原生要吃的格式。而就在目标论文发表前不久，同一个作者团队自己写过一篇 ROCm 工程博客《Productionizing TurboQuant on AMD GPUs》，把 TurboQuant 的码表方案用自研 Triton/HIP/FlyDSL 内核在 AMD GPU 上跑出约 3.6 倍的端到端提速，建议生产环境默认用 TQ4/4（K/V 都是 4 bit）——这篇博客证明了"码表方案经过足够的内核工程也能跑得不算慢"，但走的仍然是软件查表+反量化的路线，没有接入矩阵核原生支持的 scaled-MFMA 通路。

*** 为什么这招管用（以及哪里埋了新坑）
部署这条线把"省内存"变成了"真的能在生产系统里多塞几个并发请求"，而且 FP8、MXFP4/UE8M0、CDNA4 scaled-MFMA 这几样东西凑在一起，已经把"4-bit 浮点 + 块缩放 + 硬件原生反量化"这条路铺好了——缺的只是一套"离线精度验证过关、同时就是这套硬件原生格式"的方案。TurboQuant 的高精度码表和这条硬件通路之间，隔着"码表 lookup vs. 硬件原生网格"这最后一道墙，谁来把它拆掉，谁就能把质量锚点和部署锚点真正接到一起。

** 2026-06 | UltraQuant（目标论文）：把 TurboQuant 的校准码表换成硬件原生的 FP4 微缩格式

*** 它看到了什么问题
把前面两条线摆在一起看：质量锚点（TurboQuant/QJL）证明了旋转+码表能在 2-4 bit 区间逼近信息论最优精度，但码表意味着软件查表，天然跑不快；部署锚点（vLLM FP8）证明了硬件原生格式能把压缩收益真正兑现成吞吐量，但停留在 8-bit，没有触碰 4-bit 应有的那部分额外收益。而且这两条线此前都是在"短对话、单请求"式的场景下评估的，没有人专门针对 agent 工作负载——长前缀在几十个回合里反复复用、同时有几十个并发请求抢 GPU——把"任务质量、cache 能不能留得住、吞吐量"这三件事绑在一起联合测量和优化。

*** 它的解法
目标论文做了三件事：

第一，重新定义评测场景：不再用静态的困惑度曲线，而是用"adaptive-SLO replay"——用生产环境里真实的 Claude Code agent 轨迹回放，同时测质量是否达标、cache 能不能在高并发下留住、以及吞吐量，三个指标联合看。

第二，给出一套"让 4-bit 路径足够稳"的具体设计取舍：继续 KIVI/KVQuant 的思路做 K/V 非对称处理（旋转只作用在 K 上，V 不转；K 走"存块范数 + 编码到最近码表质心"，V 走"存 block 的 scale/zero + 均匀 4-bit"这种更简单的方案）；保留 Walsh-Hadamard 旋转"把异常值能量打散成近似高斯分布"这个核心道理（这正是 TurboQuant 证明有效的部分）；但把 QJL 这一步从流水线里拿掉——不再对残差做 JL 变换去偏，换成更简单的分块缩放(block-scale)变体，用工程上的简化换取在实际部署里更低的开销。

第三，也是最关键的一步：把 TurboQuant 的 Lloyd-Max 校准码表，换成 FP8 query + FP4 KV 张量 + UE8M0 分块缩放因子这套硬件原生微缩格式(microscaling)——FP4 的网格不再需要查表，UE8M0 的反量化只是一次位移，这套格式可以直接喂给 AMD CDNA4 的 scaled-MFMA 矩阵核指令去消化，不再需要软件层面的不规则内存访问。

*** 为什么这招管用（以及哪里埋了新坑）
这一步精确地把前面两条线的断点接上了：旋转依然在解决"异常值能量分布不均"这个老问题（继承自 TurboQuant 的数学道理），但解码这一步换成了和 FP8 KV cache 一样的硬件原生路径（继承自 vLLM FP8 + OCP Microscaling + CDNA4 的部署逻辑）。效果上，在 adaptive-SLO replay 的生产 Claude Code agent 轨迹上，UltraQuant 相比 BF16 做到 2.71 倍（MiniMax-M2.5）和 4.38 倍（Qwen3-235B）的"合格请求吞吐量"，在 KV 字节数只有 FP8 一半的情况下，质量追平甚至超过硬件原生的 FP8 KV cache。

新的坑也藏在这里：目标论文的摘要和正文的公开信息里，并没有给出和 TurboQuant 论文那样系统的、按 bit 数细分的离线精度曲线（比如具体在哪些任务、哪些模型上，困惑度或准确率分别掉了多少）——这一点被后来的独立评审（见"前沿延伸"）直接点名。换句话说，这篇论文把"工程落地"这件事做得很扎实，但"质量锚点"这一侧的证据链，交代得不如 TurboQuant 本身充分。

* 前沿延伸

目标论文最早挂出是 2026 年 6 月，最近一次更新是 2026 年 9 月，距今（2026-10-09）才一个多月，还没有检索到严格意义上的学术论文明确引用并批评/改进它。能找到的几条后续线索，诚实地分开说：

1. *同团队的部署延伸（确认）*：AMD 自家 ROCm 博客《UltraQuant on AMD Instinct: More Efficient Agentic Serving for Qwen3.8-MXFP4》（2026-09-25），作者是目标论文的同一批人。把 UltraQuant 应用到 Qwen3.8（一个 2.4 万亿参数的 MoE 模型，权重本身也用 MXFP4 量化）的真实 agentic serving 场景，报告在并发数 32 时比最快的 8-bit KV 后端"吞吐量高 29%、单 token 延迟低 24%、首 token 快 1.7 倍"，并验证了和多 token 预测（MTP）投机解码的兼容性。这是对目标论文方法的部署验证和场景扩展，不是独立的批评性后续工作。

2. *独立评审的质量缺口批评（部分确认）*：一个自动化论文评审站点（pith.science）指出，目标论文摘要明确说"质量、cache 占用、吞吐量必须联合测量"，但只报告了后两者，没有给出具体的任务质量数字、数据集描述或成功判据——评审认为"读者没法判断这套压缩方案到底有没有真的保住输出质量"。另有一篇讨论 AnchorKV（一篇无关的、专注安全对齐的 KV cache 压缩论文）的博客，把目标论文当反面案例引用，指出在 AIME25（高难度数学推理测试集）上，4-bit KV cache 让 Qwen3.5-A3B 掉了 13.33 分，而在 MATH500 上几乎没有影响——并提醒读者"在信任这类速度提升之前，先在高难度推理任务上测一测，而不只是看聊天场景的指标"，还指出目标论文虽然标题写的是"context-heavy agents"，但实际评测用的是 MI355X 硬件上 MiniMax-M2.5 和 Qwen3.5-A3B 跑 ShareGPT 聊天数据，并发数 32——不是 DeepSeek 系列模型，也不是严格意义上的 agentic 工作负载。这两条批评指向同一个缺口：论文的工程/部署证据很扎实，但"质量"这一环的公开证据相对单薄。需要说明的是，这些评审来自非正式渠道（自动化评审站点、独立 newsletter），不是同行评审的学术论文，应该按"值得关注的早期质疑信号"而不是"已确认的学术批评链"来看待。

3. *社区衍生项目，真实性存疑（明确标注为不可靠）*：一个名为 Minato-Hayakawa/KV-Cache-Quantization-Benchmark 的 GitHub 仓库提到，TurboQuant 发布之后，"RotorQuant"" "HyperQuant"等方法跟着冒出来，自称在多项指标上超过 TurboQuant，但该仓库本身承认这些方法"各自在不同模型、不同硬件、不同指标下独立评测，缺乏同条件下的交叉对比"；进一步检索发现 RotorQuant、HyperQuant 目前只存在于 GitHub 仓库和自媒体博客里，没有被任何学术会议接收或挂上 arXiv 的证据，且社区讨论里已经有人指出其宣称的压缩率和实测结果对不上（比如号称 3-bit 但实际 K cache 体积是同精度 q8_0 格式的两倍）。这条线索*不构成*可信的学术引用链，这里只作为"目标论文发布后，这个方向关注度上升"的侧面佐证列出，明确标注为未经证实。

综合来看：目标论文还太新，没有形成严格意义上的"后续论文批评/改进"闭环，但已经出现了两类信号——一类是自家团队把方法落地到更大模型、更真实场景（积极验证），一类是独立评审对"质量证据不够"提出具体质疑（有待目标论文后续版本或独立复现来回应）。

* 洞见

这条线真正在发生的变化，不是"压缩率数字越做越小"，而是"用什么去编码一个量化后的数值"这件事，逐渐从"怎么编码最准"转向"怎么编码最适合硬件去解码"。KIVI/KVQuant 解决的是"K 和 V 该不该用同一套方案"；QJL 解决的是"量化常数本身占不占地方"；TurboQuant 解决的是"编码能不能逼近信息论最优"——这三步全部盯着"精度"这一个目标在优化，谁都没问过"这套编码在真实 GPU 上解码要花多少钱"。而 vLLM FP8 这条平行线，恰恰完全反过来：它从一开始就只选"矩阵核原生支持"的格式，牺牲了压缩率换执行效率。UltraQuant 真正做的事情，是意识到这两条线其实可以合并——旋转让分布变得适合量化这件事和"码表 vs. 硬件网格"是两个独立的选择，完全可以把 TurboQuant 证明有效的"旋转"部分留下，把它证明"不好部署"的"码表"部分换成和 FP8 同一个硬件通路的 FP4 微缩格式。

这提示一种研究节奏：当一个领域里同时存在"精度最优但跑得慢"和"跑得快但精度有限"两条平行发展的技术线时，往往意味着有人把"编码方案"和"解码效率"这两个本可以独立调节的维度捆在了一起，默认"做到最准"就必须"牺牲速度"。真正的突破常常不是在其中一条线上继续精修，而是把两条线的组件拆开重新拼装——保留一条线证明有效的数学原理，换上另一条线证明高效的物理实现。

下一步最可能的方向：目标论文自己没有交出和 TurboQuant 同等级别的、按 bit 数/按任务细分的离线精度曲线，独立评审也已经点出这个缺口；同时，agent 工作负载里"高难度推理任务（如 AIME 级别的数学题）"在 4-bit KV cache 下到底掉多少分，目前只有一条非正式的批评信号（−13.33 分），还没有被系统地测过。补齐这两块证据，大概率是下一篇后续工作（不管是目标论文自己的修订版，还是独立复现）要做的事。

* 启发

这条演化线提示一个值得记住的视角：当你看到一个领域里"离线精度论文"和"系统部署论文"长期各自为战、互相引用对方当"background"却从没真正握手时，这个"握手点"本身就是一个还没被认领的研究机会。精度研究者习惯假设"只要算法对，工程总能跟上"；系统研究者习惯假设"只要格式简单，精度总能凑合"——两边都对自己领域之外的那部分想得太乐观。真正把两条线接起来的人，往往不需要发明全新的数学，只需要诚实地问一句："我证明有效的这个核心道理，换一种更适合硬件的编码方式之后，还成立吗？"
