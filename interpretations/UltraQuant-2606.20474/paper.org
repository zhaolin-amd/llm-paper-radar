* 问题

想象一个帮你写代码的 agent。你让它看一遍仓库、读懂某个 bug、改代码、跑测试——一个任务要来回聊六轮。每一轮它都得把前面攒下的东西记住：系统提示、工具定义、它刚读过的那几百行代码、它自己拟的计划。这些记忆存在一块叫 KV cache 的显存里，而且只会越堆越多，从不清空。

现在服务商要同时扛住 32 个这样的 agent 会话。显存是定量的，会话越往后聊，每个人占的 KV cache 越大。到了第四轮、第五轮，显存不够分了，系统只能把某些会话前面攒的记忆挤掉，等用户再问起来，模型得从头把那段上下文重新算一遍——这一算，首字延迟直接飙到原来的 3.47 倍。会话越长，这笔账越难看。

怎么办？最直接的办法是把每个数字存得更省——原来存 16 位的 BF16，改存 8 位的 FP8，显存占用砍一半，精度几乎不掉，AMD 和英伟达的硬件矩阵核心也原生认得这个格式，这是业界公认的稳妥选择。但 8 位只能省一半，想再往下压到 4 位，还得找别的招。

学术界确实有招：把每个 key 和 value 先做一次旋转（Walsh–Hadamard 变换），把本来集中在几个异常大的数值身上的"能量"打散到全部通道上，分布就变得服帖、接近正态；再配一张精心校准过的 4 位码本（codebook），每个数值查表映射到最近的码字上。这套组合拳（TurboQuant）理论上能把 4 位的精度做到很漂亮。可它有个代价：解码的时候，每一步都要去查这张表——而查表是不规则的内存访问，上下文越长，这笔开销越大，反而拖慢了实际服务的速度。于是团队撞上一个两难：FP8 省得不够，TurboQuant 省得够但跑不快。

本文的作者盯着这同一套服务场景，却从另一个角度切进去：他们没有继续在"码本够不够精细"上较劲，而是去问——显卡的矩阵核心（matrix core）本来就认识哪种 4 位格式？如果直接用那种格式存 KV cache，会发生什么？

* 翻译

还是那 32 个并发的 agent 会话、六轮对话、随时可能被挤出显存的记忆。在这个场景里，TurboQuant 的码本就像一本字典：每次要用某个词，先翻字典查它对应哪页——词典编得再好，翻的动作本身就要花时间，而且词越多翻得越久。UltraQuant 的做法是：别翻字典了，把每个数直接写成显卡"天生认识"的样子，让它看一眼就懂，不用查。

这个"天生认识"的格式，AMD CDNA4 显卡上确实存在——FP4 E2M1，4 位浮点数，配一个叫 UE8M0 的 8 位指数做缩放。矩阵核心有一条指令（scaled-MFMA），能直接吃 FP4 的数值和 UE8M0 的缩放因子，在做矩阵乘法的同时顺手把这两样东西换算回正常数值——换句话说，"翻译"这个动作被显卡焊死在了乘法指令里，根本不需要软件单独跑一趟。

问题来了：扔掉精心校准的码本，改用硬件这张"死板"的 FP4 网格，精度会不会垮掉？作者先沿用旧路的第一步——照样对 key 做 Walsh–Hadamard 旋转，把异常值的能量摊开，让分布变得近似一种叫 Beta 分布的钟形曲线（具体形状只跟"每组多少个数"这一个参数有关，跟用的是哪个模型无关）。这一步没有变化。

变化发生在"怎么把这摊开后的分布塞进 FP4 网格"这一步。原来的做法（TurboQuant）给每一个 token 算一个专属的缩放尺度（L2 范数），这个尺度精确、但要为每个 token 单独存一份、单独乘一次，而且它根本没法被直接折进后面的 softmax 计算——等于白存了。作者换了个思路：不再按 token 算缩放尺度，而是把每 32 个通道分成一组，每组自己算一个"绝对值最大值"，用这个值去除整组数字，把它们统一摊平到 [-1, 1] 区间里。这叫 per-block absmax，听起来只是换了个统计口径，但它是整套方案能不能立住的关键——后面的消融实验会证明，这一步比"码本精不精细"重要得多。

归一化之后剩下的工作，是把这摊开又收拢的数字对准 FP4 那几个固定刻度（0、±0.5、±1、±1.5、±2、±3、±4、±6）。因为分布形状已经只跟"每组多少通道"这一个参数有关，作者发现只需要离线解一次优化问题，找到一个全局常数 =c= ，就能让这摊数字整体对齐到 FP4 刻度上、误差最小——而且这个常数对任何模型都通用，不需要每上线一个新模型重新调。他们解出来的值是 =c=0.156= ，之后直接固定使用。

把这几步串起来看：key 先转一下方向（旋转），再按 32 个一组求出各自的尺度（per-block absmax），用这把尺度乘上那个万能常数 =c= ，把数字摁进 FP4 的格子里，顺手把这组的尺度存进一个 UE8M0 字节。query 这边也不含糊，直接转成 FP8。于是 QK 乘法、PV 乘法全程走的是显卡原生的 "FP8 乘 FP4" 这条硬件通道——BF16 版本的 key 和 value 从头到尾都不需要被真正算出来，压根不存在。

效果摆在数字上：在 MiniMax-M2.5 这个模型、32K 输入 + 1K 输出、64 路并发的设置下，UltraQuant 吞吐量达到 BF16 基线的 1.38 倍，跟硬件 FP8 方案的 1.37 倍几乎打平——但它占用的显存只有 FP8 的一半。放到那个六轮 agent 对话的场景里看更直观：到了后面几轮、显存真正吃紧的时候，UltraQuant 比 FP8 快 3.47 倍，因为它能在同样的显存里多留住几倍的历史对话，不用频繁挤出去重算。

但这里面藏着一个作者自己也没想到会这么明显的反转：他们专门做了一组消融实验，把"用什么统计口径定标"和"用什么码本"这两件事拆开单独测。结果是——只要把定标方式从"per-token 范数"换成"per-block absmax"，精度立刻从 0.6237 涨到 0.6559；而在这之后，再把那张精心校准的码本换成一个随便的均匀网格，精度几乎纹丝不动（0.6559 对 0.6528，在误差范围内）。也就是说，整篇 TurboQuant 故事里被当成卖点的"精心设计的码本"，其实根本不是精度的功臣——真正扛事的是"按哪种口径算缩放尺度"这一个此前没人细究的小选择。

数字背后还有一件事作者没有藏着：这套方案不是处处无损。在 AIME25（数学竞赛题）上，两个模型分别掉了 13.33 和 10.0 个百分点，比其他三项 benchmark 的波动大得多。这说明 UltraQuant 省下来的这点精度，代价集中砸在了对数值推理要求最苛刻的任务上，而不是均匀地摊在所有任务里。

这些发现背后，还有三件事在支撑整套系统真正跑起来——下一节拆开讲。

* 核心概念

** Walsh–Hadamard 旋转

一个把"异常值"摊平的操作：原始的 key、value 里，总有少数几个通道的数值特别大，像一桌菜里混进几道特别辣的——如果直接按原始数值量化，几个辣菜会把整张量化表撑得很宽，大多数清淡的菜反而被挤到没几个格子可用。旋转做的事，是把这桌菜重新搅拌一遍，让"辣味"均匀混进每一道菜里，没有哪道菜格外突出。摊匀之后，整体分布变成一条近似正态的钟形曲线——这正是后面"用固定网格量化"能够成立的前提。少了这一步，FP4 那几个固定刻度会被少数异常值逼得浪费大半：要么把量程留得够宽、覆盖异常值，代价是大多数正常值挤在中间几个格子里分辨不清；要么把格子切得精细，代价是异常值直接溢出。

** per-block absmax 定标（设计选择）

这是整篇论文真正的转折点，而不是一个无足轻重的工程细节。旧路（TurboQuant）给每个 token 单独算一个 L2 范数作缩放尺度，精确，但要为每个 token 多存一个数、多做一次乘法，而且这个尺度没法被后续的 softmax 计算吸收，纯属额外开销。作者换成了"每 32 个通道一组，组内求绝对值最大值"——这组统计量恰好可以直接变成硬件要的那个 UE8M0 缩放字节，不需要额外存储，也不需要额外的运行时乘法。消融实验证明，把定标方式从 per-token 换成 per-block，是精度提升的全部来源；而码本精不精细，在这之后已经不太重要了。少了这个设计，后面"扔掉码本改用硬件网格"这一步会直接让精度垮掉——是它先把精度兜住了，FP4 网格才敢大胆地接手。

** FP4 E2M1 + UE8M0 硬件原生网格

这是把"查表"变成"一条指令"的那个载体。FP4 E2M1 是显卡矩阵核心原生认识的 4 位浮点格式，几个固定刻度写死在硬件里；UE8M0 是配套的 8 位缩放因子，恰好是 2 的整数次幂，所以"还原数值"这件事从一次浮点乘法退化成一次指数位移——而这个位移动作直接被焊进了 AMD 的 scaled-MFMA 矩阵乘法指令里。少了这一步，就算定标和旋转都做对了，最后那张码本依然要靠软件一条一条去查、去重建，长上下文下的那部分解码延迟根本降不下来。

* 洞见

这篇论文留下的东西，不是"4 位 KV cache 又快又准"这句好看的结论，而是一句对做压缩的人更有用的话：当一个在数学上稍微不那么精确的格式恰好是硬件指令集原生认识的格式时，把算法凑近硬件，往往比把硬件凑近算法上最优的表示划算得多。

码本量化在纸面上误差更小，这点作者从没否认；但那份"更小的误差"必须靠一次软件查表才能兑现，而查表这件事在长上下文、高并发的服务场景里，本身就是真实成本。UltraQuant 选择让一点点可以量出来的数值误差，换掉一个在部署时才会发作的系统性瓶颈——这笔账在"离线跑一次 benchmark"的视角下可能不划算，但在"显卡 7×24 小时服务真实用户"的视角下是赚的。

* 博导审稿

这篇东西的问题选得很准——agent 一跑起来上下文就爆，这事不是编出来的，是现在所有做 agent 服务的团队都在吃的亏，值得认真做。

但我想戳一戳方法里那个最关键的假设：作者说"旋转之后，分布只跟 head dimension 有关、跟具体模型无关"，所以一个全局常数 =c=0.156= 能通吃所有模型。这个假设目前只在三四个模型上验证过，而且都是比较常规的注意力结构。换一种更激进的注意力变体——比如多头潜在注意力把 key、value 的几何结构改得完全不一样——这个"旋转后近似 Beta 分布"的前提还成不成立，论文自己在 Limitations 里也承认没细想，留给了以后。这不是小问题：如果这个前提在新架构上塌了，整套"一个常数通吃所有模型"的省事做法就得推倒重来，退回到"每个模型重新标定"的老路上。

第二点，AIME25 掉了十个点以上，作者没有藏着掖着，这点要给加分——很多论文会把这种刺眼的数字用"平均精度"糊过去，这篇没有。但正因为诚实，才更该追问：这个掉点的根子在哪？是旋转把某些对数值推理关键的通道信息也打散了，还是 FP4 网格本身在表示"接近整数的小数"时天生弱？论文没有往这个方向深挖，只是报了数字、认了限制。

第三点是个小瑕疵：对比的开源 TurboQuant 基线（5.56 倍 BF16 的单 token 延迟）差得有点夸张，这里面有多少是"码本查表本质上慢"、有多少是"那份开源实现本身没被精心优化"，论文没有拆开讲——用一个优化得不够的对照组，容易把自己这边的提升显得比实际更大。

综合看：工程做得扎实、诚实披露了短板，但"一个常数通吃所有模型"这个核心假设验证样本还太薄，AIME25 的掉点也没查到根子。weak accept——值得发表，也值得在更多模型架构上再跑一遍再信。

* 启发

*迁移*：下次做任何"压缩 + 硬件部署"的活，先别急着设计数学上最优的码本或量化方案，先去问一句——目标硬件这块芯片原生认识的最小格式是什么？把算法往这个格式上靠，很可能比死磕"理论最优表示再想办法塞进硬件"更省事、更快落地。这条思路不只适用于 KV cache，权重量化、激活量化遇到同样的"理论最优 vs 硬件原生"的岔路时都能照搬着问一遍。

*混搭*：per-block absmax 这招——用一组固定大小的通道求绝对值最大值来定标，代替按 token 或按 channel 的复杂归一化——值得直接搬到别的低比特量化场景里试一把：权重量化、激活量化，但凡现在还在用更复杂的归一化统计量，都可以先换成这个最朴素的版本测一测，说不定复杂的那部分本来就是冗余的，就像这篇论文里码本的处境一样。
